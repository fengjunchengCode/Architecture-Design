# Development Contract

本文件定义本仓库的开发改动守则。来源参考：

- `multica-ai/andrej-karpathy-skills`
- `https://github.com/multica-ai/andrej-karpathy-skills`

这些规则用于所有代码、工具、UI、schema、skill 和文档修改。它们不替代业务 workflow；它们约束 agent 如何修改本仓库。

## 1. 编码前先澄清

不要默默选择一个解释然后实现。

- 需求存在多种解释时，先列出解释和取舍。
- 如果用户指出方向不对，先停下来重读需求，不继续扩写当前方案。
- 对非琐碎改动，先写成功标准，再动手。
- 若更简单的方案能满足目标，应主动提出。

## 2. 简洁优先

只实现当前目标需要的最小方案。

- 不添加用户没有要求的功能。
- 不为一次性逻辑抽象出框架。
- 不为了“以后可能用”增加配置、插件、状态机或复杂 UI。
- 如果改动明显臃肿，应先缩小范围。

## 3. 精准修改

每一处 diff 都必须能追溯到用户当前请求。

- 不顺手重构相邻代码。
- 不改动无关注释、格式或文件结构。
- 匹配现有代码风格，而不是换成个人偏好。
- 只清理本次改动产生的无用代码；旧的无关问题只记录，不擅自删除。

## 4. 目标驱动与验证闭环

把“做某事”转成可验证目标。

- bug 修复：先说明如何复现或验证。
- UI 修改：先说明目标用户流程和验收标准，再实现。
- 工具修改：提供命令级验证，例如 `selfcheck`、脚本 `--check`、API smoke test。
- 多步骤任务：用“步骤 -> 验证”组织计划，并在完成后报告哪些验证已通过、哪些没跑。

## 5. 本项目执行落点

- 修改上传 UI 前，先定义页面层级、用户路径和当前屏只承担的一个主任务。
- 修改 S1/S2/S3 等 skill 前，先确认 marker 写入范围和下游交接口。
- 修改 schema 前，先确认是否真的需要新核心字段；派生数据优先放 `05_output/` 子目录。
- 添加工具前，优先做确定性 CLI，再接 UI；UI 只调用工具，不把业务逻辑散在前端。
- 遇到需求偏差时，暂停实现，先回到本文件的四条原则重新校准。
